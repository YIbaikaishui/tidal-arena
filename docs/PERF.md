# 性能排查与调优（帧率低怎么办）

> 2026-10-20 / 21 实测记录。数据来自本机 `tools/perf_bench.cjs` 等无头 Chromium 探针。
> 测试机：Intel UHD 核显 + RTX 4060（浏览器默认走核显），1600×900。

## 零、轻量模式（默认开启）

面向「点开就想看一眼」的场景，**默认启用**，包含三件事：

| 手段 | 实现位置 | 效果 |
|---|---|---|
| 坐席抽稀（每 3 个渲染 1 个，切向放大 3 倍填满） | `src/lib/seats.js` `iterSeats(tiers, stride)` + `src/scenes/arena.js` | 面数 103 万 → 58 万，远景仍是连续色带 |
| 植被/城市减量 | `src/scenes/env.js` `TREE_CAP` / `HEDGE_DIV` | 减少 draw call 与实例矩阵更新 |
| 关泛光 + 关阴影 + 关颗粒/色差，补 1.14 倍曝光 | `src/lib/postfx.js` `setPerfMode` | 泛光单独就占约 **8.5fps** |
| 纹理按半尺寸生成（`setTextureScale(0.5)`） | `src/lib/textures.js` `SZ()` | 首屏 Canvas 绘制与上传开销降到约 1/4 |
| 像素预算 0.9M、像素比上限 1.0 | `src/lib/core.js` `PIXEL_BUDGET.lite` | — |

开启方式：默认即是；`?full=1` 关闭；`?lite=1` 强制开启；设置面板「轻量模式」开关（切换需刷新）。
`__setLiteMode(true/false)` 也可在控制台调用。

**⚠️ 容量统计不受影响**：`seatModel()` 恒用 `stride=1`，座位总数始终是 80,952，HUD 与疏散数据不变。

### 实测对比（1600×900，Intel UHD，冷启动）

| 配置 | 面数 | 帧率 | 备注 |
|---|---|---|---|
| 完整档 `?full=1` | 103 万 | ~20–23 fps | 泛光 + 阴影 + 全量几何 |
| 轻量档 `?lite=1` | 58 万 | ~27–32 fps | 无泛光、无阴影、坐席抽稀 |
| 轻量档 + 重新打开泛光 | 58 万 | ~24 fps | 验证泛光本身的成本 |

> 测量受本机其他程序（常驻 20+ 个 Chrome 进程）干扰，绝对值有波动，
> 但「轻量档 > 完整档」与「泛光 ≈ 8.5fps」这两个相对结论稳定复现。

**注意：`iterSeats` 的 `stride` 只影响渲染实例，绝不能传给 `seatModel()`**，
否则座位总数会随画质变化，HUD、疏散、容量统计全部错乱。

## 一、先判「是不是程序的问题」

页面运行后按 **Shift + P**，右下角出现诊断面板：

```
帧率      17.4 fps   ← 偏慢
GPU       ANGLE (Intel, Intel(R) UHD Graphics ...)   ← 这里写的是什么卡，就是什么卡在跑
像素比    1.24  (2102×1237)
预算      高性能 2.6M  档位 mid
绘制      245 call / 1.02M 三角面
省电模式  关（Shift+P 开启）
```

| 诊断面板显示 | 结论 | 处理 |
|---|---|---|
| `GPU` 里出现 **SwiftShader / Basic Render** | 浏览器根本没用到显卡（软渲染），会慢到个位数帧率 | 页面会弹出提示页；开 `chrome://settings/system` 的「使用图形加速功能」并重启浏览器 |
| `GPU` 是 **Intel UHD / 核显**，但机器有独显 | 浏览器被系统分配给了核显（笔记本拔电 / 显卡驱动电源策略） | 插上电源；NVIDIA 控制面板 → 管理 3D 设置 → 程序设置 → 给 chrome.exe 选「高性能 NVIDIA 处理器」 |
| `GPU` 是 NVIDIA，但帧率仍 < 40 | 填充率瓶颈，正常现象，按下面的「省电模式」处理 | 开省电模式 |
| `帧率 ≈ 60` | 程序没问题，是这个页面的正常上限（rAF 锁 60） | 无需处理 |

## 二、已做的优化（本次）

| 改动 | 位置 | 效果（实测，1700×1000@1.25 DPI 无头） |
|---|---|---|
| 新增 **省电模式**：像素预算 2.6M → 1.3M、关泛光 mip 链、关阴影投影 | `src/app.js` `detectPerfMode/setPerfMode`、`src/lib/postfx.js` `setPerfMode`、`src/lib/core.js` `PIXEL_BUDGET` | 恒定的高负载视角下 **18.7 → 24.3 fps（+30%）**；分辨率减半时（1.3M 像素）可到 ~30fps |
| 阴影从 `PCFSoftShadowMap` 换成 `PCFShadowMap` | `src/lib/core.js` | 每个采样点 4 次纹理读取 → 1 次；视觉差异可忽略（且可在省电模式整体关闭阴影） |
| **Shift+P 诊断面板** | `src/app.js` `showPerfHud` | 一眼看出「是不是跑在核显/软渲染上」，这是最常见的「莫名很慢」根因 |
| **软渲染拦截页** | `src/app.js` `showSoftwareWarning` | 不再无声卡死，给出可操作的三步修复指引 |
| 持续掉帧时记忆并在下次启动默认进省电档 | `src/app.js` `watchPerf` / `detectPerfMode` | 同一个人下次打开直接是流畅档 |
| 上下文丢失（驱动重置/显存回收）提示 | `src/lib/core.js` + `src/app.js` | 不再白屏无解释 |
| 性能自适应阈值放宽到 38fps 并保留 | 原有 `fnLog` / `ui.update` | 持续 <38fps 自动降质 |

省电模式的三种开启方式：设置面板 → 「省电模式」开关、URL 加 `?perf=1`、控制台 `__setPerfMode(true)`。

## 三、还没做、但收益最大的（需要先拿数据再动手）

实测每组「关掉某个东西」的帧率增量（同一机位，Intel UHD 核显，自动降质后的状态）：

| 关闭项 | 帧率 | 增量 |
|---|---|---|
| 基准 | 18.7 | — |
| 关泛光 | 16.9* | ≈ 0（已被自动降质关掉时） |
| 关掉全部后期（直出） | 19.2 | +0.5 |
| **隐藏坐席（103 万面 → 35 万面）** | **26.4** | **+7.7** |
| **隐藏周边城市/环境层** | **33.8** | **+14.6** |
| 隐藏天穹 | 60.4 | — |

结论很明确：**瓶颈是「百万级三角面的顶点处理 + 填充」，不是后期处理。**
其中坐席（`seats-L1/L2/L3`，四个 InstancedMesh 合计约 120 万顶点）和周边城市层是两块大头。

按投入产出排序，下一步建议：

1. **坐席 LOD**（收益最大、改动集中在 `src/scenes/arena.js` 的坐席生成段）
   远景/俯视时用低细节坐席几何（每排每区只保留 1 个面片或降采样排数），
   只在高机位切换，切换时用 `InstancedMesh.count` 做裁剪，不需要重建几何。
2. **周边城市层视距裁剪**（`src/scenes/env.js` 的 `gCity`）
   城市体块只在离镜头一定距离内可见；漫游时基本在城市外沿，可整体隐藏。
3. **首屏耗时**：目前冷启动约 5.3s，大头是 `textures.js` 里 2048×1400 / 1024×512 的程序化纹理
   与逐排逐区生成坐席几何；可把坐席几何改为「空闲任务分片生成」（`requestIdleCallback`），
   让首屏先出画面再补细节。

## 四、复现测量

```bash
cd tools
node perf_bench.cjs            # 四组配置对比
node perf_bench.cjs --headed   # 有头模式，更接近真实观感
```

`_perfprobe.cjs` / `_perfprobe3.cjs` 是逐项拆解脚本（关泛光、关各层、读绘制量），改优化时用它定位瓶颈。
